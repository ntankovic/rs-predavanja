# Sources and asset provenance

Accessed 2026-11-09 unless stated otherwise. Quotes were checked verbatim on the page unless marked.

## References

1. M. Kleppmann, *Distributed Systems*, lecture notes, University of Cambridge, 2021/22. https://www.cl.cam.ac.uk/teaching/2122/ConcDisSys/dist-sys-notes.pdf (also `references/legacy/dist-sys-notes.pdf`). §1.3 pp. 8–11: stub "has the same type signature as the real function"; marshalling; location transparency "system hides where a resource is located"; four questions (crash, lost, delayed, safe to retry); RPC history list incl. gRPC (Google, 2015); IDL generates stubs; fetch example with three outcomes; cites Waldo et al. 1994. §5.1 pp. 47–48: deduplication "requires storing requests ... in stable storage" in a crash-recovery model; idempotence f(f(x)) = f(x); likeCount vs likeSet; at-most-once / at-least-once / exactly-once = "retry + idempotence or deduplication"; "the update may actually be applied multiple times, but the effect is the same as if it had been applied exactly once".
2. gRPC, "Core concepts, architecture and lifecycle". https://grpc.io/docs/what-is-grpc/core-concepts/ — unary RPC "just like a normal function call"; compiler plugins "generate client- and server-side code"; "both the client and server make independent and local determinations of the success of the call, and their conclusions may not match".
3. gRPC, "Deadlines". https://grpc.io/docs/guides/deadlines/ — "By default, gRPC does not set a deadline"; "always explicitly set a realistic deadline"; DEADLINE_EXCEEDED; server may "periodically check if the RPC ... has been cancelled"; propagation "supported by some gRPC implementations".
4. gRPC, "Retry". https://grpc.io/docs/guides/retry/ — "configurable via gRPC Service Config, at a per-method granularity"; example maxAttempts 4, retryableStatusCodes ["UNAVAILABLE"]; "Without a retry policy, gRPC cannot safely retry RPCs in most cases"; "Once the response header is received, the RPC is committed. No further retries will be attempted".
5. Protocol Buffers, "Language Guide (proto 3)". https://protobuf.dev/programming-guides/proto3/ — field number "cannot be changed once your message type is in use"; "should never be reused"; unset field "will not be serialized to the wire" and returns the default; "Proto3 messages preserve unknown fields and include them during parsing and in the serialized output".
6. Protocol Buffers, "Encoding". https://protobuf.dev/programming-guides/encoding/ — "The binary version of a message just uses the field's number as the key".
7. Protocol Buffers, "Proto Best Practices" (moved from programming-guides/dos-donts). https://protobuf.dev/best-practices/dos-donts/ — "Never re-use a tag number"; "reserved 2, 3;".
8. RFC 9110, "HTTP Semantics", June 2022, §9.2.1–9.2.2. https://www.rfc-editor.org/rfc/rfc9110.html — safe = "essentially read-only"; idempotent definition; "PUT, DELETE, and safe request methods are idempotent"; client may "establish a new connection and retry the idempotent request".
9. Stripe, "Idempotent requests". https://docs.stripe.com/api/idempotent_requests — saves status code and body of the first request; retries return it "including 500 errors"; compares parameters and errors if different; keys may be removed after "at least 24 hours".
10. J. Jena, S. Dalal, A. Tishkin, "The Idempotency-Key HTTP Header Field", draft-ietf-httpapi-idempotency-key-header-08 (Internet-Draft, active, last updated 2026-10-22; not an RFC). https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/ — "An idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries of the same request."
11. M. Brooker, "Timeouts, retries, and backoff with jitter", Amazon Builders' Library, 2019. https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/ (redirects to builder.aws.com) — "Retries can amplify the load"; retries at each layer multiply; start timeouts from downstream latency metrics and a percentile such as p99.9.
12. M. Ulrich, "Addressing Cascading Failures", Site Reliability Engineering, ch. 22. https://sre.google/sre-book/addressing-cascading-failures/ — "a single user action may create 64 attempts (4^3) on the database"; "servers should employ deadline propagation"; tree of RPCs shares "the same absolute deadline".
13. RFC 5531, "RPC: Remote Procedure Call Protocol Specification Version 2", May 2009, §5. https://www.rfc-editor.org/rfc/rfc5531.html — server "may wish to remember previously granted requests ... to insure some degree of execute-at-most-once semantics" using the transaction ID, and a client "may choose to reuse its previous transaction ID when retransmitting"; "If it does receive a reply, then it can infer that the procedure was executed at least once"; without a reply "it cannot assume that the remote procedure was not executed".
